# JIT Decision v1

Version: **1.0.0**

Status: **DEFER**

Decision date: **2026-08-04**

```text
M6 LLVM JIT = DEFER
```

## GO conditions (all must hold)

1. Interpreter dispatch/execution accounts for at least 40% of CPU in at
   least two product workloads.
2. Host boundary and GC are no longer the first bottleneck.
3. Hot spots concentrate in a small set of long-lived functions.
4. Warm V8 still leads Nexa by at least 1.5x on at least three comparable
   pure-computation workloads.
5. LLVM compilation cost amortizes within the frozen call-count or
   frame-count budget.
6. ValueLayout, ExecutableModule, safepoints, root maps, and the Host ABI
   are frozen.

Otherwise the decision is `DEFER`, and if GC or the Host boundary remains
the first bottleneck, the next milestone is a targeted M5R1 rather than a
JIT.

## Final evidence

The formal Benchmark v7 qualification used 7 independent processes and 1,000
samples per process. All M5 throughput buckets passed, no unexplained p95/p99
regression remained, incremental GC allocated no system memory, and all six
steady-state Engine dispatch paths allocated no system memory.

The GO conditions resolved as follows:

1. **Not proven.** The profiler recorded 37,459,510 opcode executions and a
   70.47% top-five opcode share, but opcode counts are not CPU samples. There
   is no per-workload sample proving interpreter dispatch/execution consumes
   at least 40% of CPU in two product workloads.
2. **Satisfied.** The formal incremental-GC p50 was about 1.04us with zero
   system allocations; Host-boundary allocation behavior is contract-pinned
   and is not the first measured bottleneck.
3. **Satisfied.** The bounded profile recorded 21 functions with zero dropped
   functions, demonstrating concentrated, fully retained hot-function
   evidence.
4. **Satisfied.** Node v26.6.0 / V8 14.6.202.34-node.26 produced identical
   results with zero semantic mismatches. Warm V8 led the three comparable
   pure-computation workloads by 67.19x, 162.48x, and 156.39x.
5. **Not proven.** No LLVM prototype measures compilation cost or proves that
   cost amortizes within a frozen call-count or frame-count budget.
6. **Satisfied at publication.** The annotated `performance-m5-complete` tag
   freezes ValueLayout, ExecutableModule, safepoints, root maps, and the Host
   ABI at the clean published HEAD; the finalizer rejects any other state.

Because every GO condition is mandatory, conditions 1 and 5 force `DEFER`.
The large V8 gap is evidence that native execution may eventually be valuable,
but it is not permission to add LLVM without first attributing real product CPU
time and measuring compile-cost amortization.

## V8 comparison discipline

The V8 comparison is a decision input, not a completion gate. The
comparison report pins the V8/Node version, warmup protocol, and workload
mapping; it acknowledges that warm V8 is JIT-compiled code measured against
the Nexa interpreter. Absence of a working V8 environment on the
qualification machine blocks the decision report, not the rest of M5.
